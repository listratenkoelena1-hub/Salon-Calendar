# Dash Booking sync

Эта ветка подготавливает двустороннюю синхронизацию Rose Calendar и Dash Booking без официального Dash API. Интеграция использует только видимый партнёрский интерфейс Dash и по умолчанию полностью выключена.

## Что синхронизируется

### Rose Calendar → Dash Booking

- активный appointment создаёт `Block Time` у соответствующего мастера;
- перенос, изменение времени, длительности или мастера обновляет блок;
- при смене даты или мастера сначала создаётся новый блок, затем удаляется старый — время не остаётся случайно открытым;
- cancel, no-show и delete удаляют только тот Dash-блок, который ранее создала эта интеграция;
- `OffWork`, weekly off и материализованные дни vacation также создают `Block Time`;
- одинаковые активные weekly-off правила предварительно сворачиваются: более
  новое правило определяется по Firestore `createTime`, старое не создаёт второй
  блок;
- pending-запрос Rose Online Booking и записи, пришедшие из Dash, обратно в Dash не блокируются;
- в описании Dash-блока нет имени, телефона или сервиса клиента: только техническая ссылка вида `Rose Calendar | appt:<id>`.
- каноническое сравнение использует `дата + мастер + начало + продолжительность`,
  где `конец = начало + продолжительность`; формат `start/end` в Dash и
  `start/duration` в Rose поэтому сравнивается одинаково;
- частичный ручной Block Time не перекрывается вторым блоком: старый блок
  удаляется, создаётся точный интервал Rose Calendar, а при ошибке создания
  выполняется попытка восстановить старый интервал.
- если мастер отсутствует в списке `Working Staffs` выбранного дня, Dash уже
  закрыл ему весь день своим рабочим графиком; аудит считает этот день покрытым
  и не предлагает лишний Block Time.

Изменения сначала попадают в идемпотентную очередь. Запуск раз в 15 минут обрабатывает ближайшие даты первыми. Перед созданием блок ищется по уникальной подписи: если прошлый запуск успел сохранить блок в Dash, но не успел записать связь в Firestore, существующий блок подхватывается без дубля.

### Dash Booking → Rose Calendar

- в активные часы читаются уведомления `New Dash Booking Appointment`, `Appointment Canceled` и `Appointment Rescheduled`;
- из карточки берутся клиент, дата, время, длительность, сервис и мастер;
- если время свободно, создаётся обычный уже подтверждённый appointment с источником `dash_booking` и подписью `@DashBooking`;
- менеджер и назначенный мастер получают `Important`, остальные сотрудники — обычное сообщение;
- дополнительного Confirm/Decline нет: Dash уже подтвердил appointment клиенту;
- отмена клиента помечает appointment canceled, сохраняет причину и освобождает его schedule slots;
- перенос обновляет дату, время, длительность и мастера, освобождая старые slots и резервируя новые;
- если при создании или переносе есть appointment/off-work conflict, календарная запись не меняется, а команда получает сообщение с просьбой решить конфликт;
- обработанный Dash ID сохраняется в закрытом receipt, поэтому одно уведомление не импортируется повторно.
- Dash не показывает отдельный ID уведомления в списке. Если два одинаковых уведомления появились в одну минуту, функция перечитывает всю маленькую совпавшую группу и окончательно устраняет дубли по ID самой Dash-записи.

### История клиента Dash

В карточке Dash контактные данные замаскированы, но ссылка клиента содержит
стабильный внутренний `cid`. Это ID клиента, а не номер appointment. Сырой `cid`
не пишется в публичный appointment и не используется как имя документа. Сервер
хеширует его и создаёт закрытые `clientLookup`, `clientProfiles`,
`appointmentPrivate` и `clientAppointmentHistory`. Поэтому повторные Dash booking
одного клиента получают общую историю мастеров, сервисов и длительности даже без
доступа к телефону или email. Если Dash перестанет отдавать `cid`, такой
appointment сохраняется без client history, но сам импорт не блокируется.

## Соответствие мастеров

В коде зафиксированы текущие Dash ID и варианты имён:

- Luba ↔ Luba / Люба
- Olha ↔ Olha / Olga / Ольга
- Olena ↔ Olena / Elena / Олена / Елена
- Iryna ↔ Iryna / Irina / Ирина
- Inna ↔ Inna / Инна
- Natalia ↔ Natalia / Natalya / Natasha / Наталья / Наташа
- Cindy ↔ Cindy / Синди
- Lan ↔ Lan / Лан
- Tanya ↔ Tanya / Tatiana / Tatyana / Таня / Татьяна
- Anystaff Is Okay :) ↔ Anyone

Sadaf намеренно не сопоставлена: её нет в текущем списке Dash. Несопоставленный мастер не выбирается приблизительно — операция останавливается и появляется закрытая запись в `dashSyncIssues`.
После добавления точного сопоставления такой входящий request автоматически проверяется снова, а будущие исходящие блоки пересобираются на заданный горизонт.

Точные переопределения можно хранить в закрытой коллекции `dashStaffMappings`, документ с ID локального мастера:

```json
{
  "enabled": true,
  "localStaffId": "local-id",
  "dashStaffId": "dash-id",
  "dashName": "Exact Dash Name"
}
```

## Закрытые коллекции

Браузер любого пользователя не может читать или менять:

- `dashSyncQueue`
- `dashSyncLinks`
- `dashIncomingReceipts`
- `dashSyncRuns`
- `dashSyncConfig`
- `dashStaffMappings`
- `dashSyncIssues`
- `dashSyncAudits`

Cloud Functions работают через Admin SDK и обходят клиентские Firestore Rules.

## Безопасное включение

Отсутствующий `dashSyncConfig/runtime` означает полный `disabled`. Рекомендуемый порядок:

1. Задеплоить rules, index и functions, не создавая активный config.
2. Создать Firebase secrets `DASH_BOOKING_EMAIL` и `DASH_BOOKING_PASSWORD`. Значения не хранить в Git или Firestore.
3. До любого включения записи выполнить отдельный 30-дневный read-only отчёт
   вне интерфейса календаря. Экспериментальное окно аудита и его callable-функции
   удалены: менеджерский календарь не зависит от Chromium-аудита и не содержит
   скрытой кнопки. Отчёт составляется напрямую и показывается в рабочем диалоге;
   он не создаёт и не меняет appointments или Block Time.
   Каждая видимая часть многосервисного appointment открывается для чтения и
   сворачивается по реальному Dash `aid`, поэтому три услуги одной записи не
   считаются тремя клиентами.

4. Создать `dashSyncConfig/runtime` в режиме наблюдения:

```json
{
  "enabled": true,
  "writeEnabled": false,
  "inboundEnabled": false,
  "initialApplyEnabled": false,
  "dailyReconciliationEnabled": true,
  "horizonDays": 30,
  "queueLimit": 25
}
```

Создание/изменение config автоматически строит очередь на заданный горизонт. При `writeEnabled: false` Dash не меняется: действия только отмечаются как dry run. Если одновременно выключен `inboundEnabled`, Chromium в этом режиме вообще не запускается — предварительный результат строится только из закрытой очереди.

5. Проверить read-only отчёт, `dashSyncRuns`, `dashSyncIssues`, даты, мастеров и количество будущих записей.
6. Отдельно утвердить пакет первоначальной синхронизации. Сам preview-отчёт не содержит и не показывает кнопку применения.
7. Включить `writeEnabled: true` и проверить несколько специально созданных тестовых appointment/off-work. Изменение флага повторно собирает очередь, включая элементы dry run.
8. Только после исходящей проверки включить `inboundEnabled: true`.

Первый цикл после первоначального включения `inboundEnabled` является безопасной
исходной точкой: до 50 уже видимых уведомлений поддерживаемых типов
прочитываются и запоминаются как `baseline`, но не создают исторические requests в
Rose Calendar. Начиная со следующего цикла импортируются только новые Dash ID.
Включать входящее направление лучше в спокойные несколько минут, чтобы новая
запись не появилась ровно посреди одноразового baseline-прохода.

Для аварийной остановки достаточно поставить `enabled: false`. Уже созданные Dash-блоки при этом не удаляются автоматически. Возврат к работе выполняется через `enabled: true`; полная сверка снова строит очередь.

## Ежедневная сверка и стоимость

- после включения `inboundEnabled` Chromium работает в `America/Edmonton`: в 06:00, 07:00 и 08:00, затем каждые 15 минут с 09:00 до финальной проверки в 19:00;
- с 19:01 до 05:59 обращения к Dash не выполняются; ночные локальные изменения безопасно остаются в очереди до 06:00;
- в 06:00 перед открытием Dash заново строится очередь сегодняшнего дня и нового дальнего края окна (для 30 дней это `today + 29`), поэтому recurring WeeklyOff остаются закрыты заранее без ежедневного перечитывания всего месяца;
- это 44 browser-run в сутки вместо 96; технический scheduler продолжает просыпаться каждые 15 минут, но вне активного окна немедленно завершается без Chromium и Firestore;
- до включения входящих уведомлений браузер запускается только когда есть реальная исходящая запись в Dash; пустые циклы и dry run обходятся без Chromium;
- будущие изменения попадают в очередь сразу через Firestore triggers;
- `horizonDays: 30` всегда означает ровно 30 календарных дат, включая начальную дату; полный горизонт используется при первом включении, изменении `writeEnabled` или `horizonDays`, а не каждую ночь;
- если импортированный Dash appointment стал короче в Rose Calendar, подтверждённая запись Dash не редактируется: синхронизация убирает только ранее созданный дополнительный хвост и создаёт одно Important-сообщение о несовпадении для ручной проверки;
- каждый созданный или принятый Block Time повторно открывается безопасным кликом, и в `dashSyncLinks` сохраняются настоящий Dash `aid` и edit URL; элемент без подтверждённого ID остаётся в очереди как ошибка и не считается успешно синхронизированным;
- Firestore хранит только маленькие технические документы, без телефонов и клиентских данных в очереди.

Главная стоимость — время 1 GiB Cloud Function с headless Chromium. Firestore и два scheduler job дают сравнительно малую нагрузку. Точная сумма зависит от реальной скорости Dash и числа блоков; её нужно проверить по Billing после первых суток dry run и первых суток записи.

## Ограничения первой версии

- это browser automation, а не официальный контракт Dash: изменение DOM, CAPTCHA или дополнительная проверка входа остановят цикл безопасной ошибкой;
- между локальным сохранением и ближайшим 15-минутным циклом остаётся короткое окно возможного двойного бронирования;
- точность чтения зависит от видимого DOM Dash; при изменении интерфейса аудит или цикл завершается безопасной ошибкой;
- никакие Save/Delete действия в живом Dash нельзя тестировать без отдельного согласования и специально выбранной тестовой записи.
